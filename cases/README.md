# Conformance cases

The benches of the language folders ([`go/`](../go), [`typescript/`](../typescript), [`java/`](../java)…) measure how fast each library is and how it behaves on the official ZUGFeRD corpus, where almost every file is valid. This folder answers another question: **which rules of a country does a library actually enforce?** It holds documents whose expected verdict and expected rules are known, runs every library of the benches on them, and gives each library a **confidence score per country**, out of 100.

The first country is Germany: the EN 16931 rules and the XRechnung 3.0.2 rules, in the CII and UBL syntaxes. The hybrid PDF formats (ZUGFeRD, Factur-X) and the other countries come later.

| File | Contents |
|---|---|
| [`suites.tsv`](suites.tsv) | The suites: syntaxes, countries, title, reference validator, external files, rules of the norm the reference does not check |
| [`cases.tsv`](cases.tsv) | One line per document: suite, syntax, SHA-256, expected verdict, expected rules, the rules the case was written to break, note |
| `en16931/`, `xrechnung/` | The mutation cases, generated by [`gen.sh`](gen.sh) |
| `external/` | The official test files, fetched by [`fetch.sh`](fetch.sh), not versioned |
| [`confirm.sh`](confirm.sh) | Runs the reference validator and records its verdicts in `cases.tsv` |
| [`cases.go`](cases.go), [`markdown.go`](markdown.go) | Go package `github.com/ritoon/invoice-bench/cases`: reads the files, scores the libraries, writes the tables (used by both report tools) |
| [`tool/`](tool) | `go run . index` lists the documents in `cases.tsv`; `go run . confirm DIR` fills in the verdicts from the reference's outcomes |

**Mutation cases.** The rule packages of [ZeRechnung](https://github.com/ritoon/zerechnung) (MIT) test each rule on mutations of a valid document: one element is removed, duplicated or given a wrong value, so as to break one rule. Their `TestVariants` tests write these documents with the rules each one was written to break (package `internal/variants`). `gen.sh` runs them at commit [`9b9f489`](https://github.com/ritoon/zerechnung/commit/9b9f489814bb03ca48b4c4a869b185441e5bfbc2) (or on the clone `ZERECHNUNG_DIR`): `internal/rules/en16931` and `internal/rules/ubl` for the `en16931` suite, `internal/rules/de` for the `xrechnung` suite. The rules the case was written to break go into the `intent` column; they are not the expected rules.

**KoSIT test suite.** The 86 business and technical cases of the official [XRechnung test suite](https://github.com/itplr-kosit/xrechnung-testsuite) (Apache-2.0), release v2026-08-31 for XRechnung 3.0.2, commit `44c3905`: all valid, all in the `xrechnung` suite. `fetch.sh` fetches them under `external/` at this commit.

## The reference

The expected verdict and the expected rules come from a **reference validator**, never from the library that produced the case. For both suites, it is the **KoSIT validator 1.6.3** with the official **XRechnung 3.0.2 configuration** of 2026-08-31 (CII D16B and UBL 2.1 schemas, CEN EN 16931 schematron 1.3.16, KoSIT XRechnung schematron 2.6.0, with the custom levels of its scenarios), the validator the German administration publishes. `confirm.sh` runs it through the Java bench (`java/`, library `kosit-validator`) and `tool confirm` records, for each document:

- **valid** when the reference raises no error (warnings and information do not count);
- **invalid** with the rules it raises as errors, `XSD` when its schema rejects the document: KoSIT then does not run the schematrons;
- **excluded** when it cannot judge the document; the reason is in the `note` column. Two cases are left out: the CEN schematron fails on two `LineTotalAmount` (`cii-053`) and the XRechnung schematron on two payment terms (`ubl-025`), with an XPath type error.

What the reference says often differs from what the case was written to break:

- 35 mutation cases are **valid** for the reference: the rule they break is a warning in the KoSIT configuration (CII-SR-002, most UBL-CR rules, for example). They check that a library does not reject what the reference accepts.
- 63 invalid cases are rejected by the **schema alone** (`XSD`). For these, raising the rule the case was written to break counts as raising the expected one (see below).
- 71 others are invalid under other rules, or under more rules, than the intended one.

`tool index` keeps the verdict of a document whose SHA-256 has not changed and marks the others `-`, to confirm: after `gen.sh`, run `confirm.sh` again.

## The score

Each library validates every document, with the most complete rule set it has offline (as in the benches), and its harness records the number of errors, the rule identifiers it reports, and any exception. A library is scored on each **part**, one suite in one syntax (four parts for Germany):

- **S**, the share of the valid cases it accepts (no error, no exception);
- **D**, the detection: for each expected rule of the invalid cases, the mean, over the cases that expect it, of a credit of **1** when the library raises the rule, **0.5** when it rejects the document under another rule or with an exception, **0** when it accepts it; then the mean over the rules, so that each rule weighs the same, however many cases test it;
- **score = 100 × √(S × D)**: rejecting everything gives D = 0.5 at best but S = 0, accepting everything gives S = 1 but D = 0; both score 0.

**Rules the reference does not check.** No CEN artifact implements BR-CO-25 (a positive amount due, BT-115, requires a payment due date, BT-9, or payment terms, BT-20), in CII or in UBL; the KoSIT configuration only has a test that monitors its implementation. The base document of the `en16931` CII mutation cases has a positive amount due and neither: the reference accepts it, a library that applies the rule as the norm writes it rejects it. `suites.tsv` lists such rules in its `unchecked` column: a valid case that a library rejects under these rules alone, every reported rule carrying one of their identifiers, counts as accepted, and the tables say for which libraries. A library that reports no identifiers cannot benefit from it.

The score of a country is the mean of the scores of its parts. A library that does not read a syntax rejects (or fails on) all its documents, hence S = 0 and a part at 0; a library not run on a suite also counts 0 for its parts. An outcome missing from a run counts as an exception.

**Comparing the rules.** The rule identifiers are compared after normalization (`Normalize` in `cases.go`): upper case, identifiers found inside messages (`[BR-CO-10] …`), and the equivalences of `equivalents`: the code list assertions of the Factur-X 1.09.2 schematron of EN 16931 map to the CEN rule on the same element, and the IGIC and IPSI rules that CEN 1.3.17 renamed compare under their new names (BR-AF-\* as BR-IP-\*, BR-AG-\* as BR-IG-\*; the reference runs CEN 1.3.16). A schema violation reported without a rule identifier (an XSD error, `cvc-…` from Xerces, "This element is not expected" from libxml2) is read as `XSD`. When the reference stopped at the schema, raising one of the rules in the `intent` column also gets credit 1: a library without a schema check that finds the broken rule has found the defect.

A library that reports messages without rule identifiers can still score: each rejection of an invalid document gets 0.5. The "Rules raised" tables of the reports show, by family, how many expected rules a library raises under their identifier.

## Limits

- **Selection bias.** The mutation cases come from ZeRechnung's own tests: ZeRechnung was written against them, the other libraries were not. Its score is an upper bound. The KoSIT test suite, written independently, makes up 86 of the 208 valid cases.
- **The reference has its own levels.** KoSIT raises some CEN warnings to errors (CII-SR-452 to 454, 465 and 466) and lowers some errors to information depending on the profile (BR-CL-10/11/24/25/26 for the extension, BR-CO-16 and UBL-CR-470 for the UBL extension, BR-CL-13 for the CVD profile), and leaves the BR-CL-21, BR-CL-23, CII-SR-475 and CII-SR-476 assertions out. A library faithful to CEN alone loses points on these rules. The Saxon floors of the polyglot bench apply the same levels, which is why they score like the reference.
- **The schema counts as one rule.** The 63 documents the reference rejects on its schema alone all expect `XSD`, which weighs like any other rule of their part: a library without a schema check that misses some of them loses little. The XSD floors catch all 63 and score about 11, since they check no business rule.
- **Errors only.** Warnings do not count, either from the reference or from the libraries.
- **Germany only, XML only.** No hybrid PDF, no Peppol, no French or other national rules yet. A library whose country is not covered is not rated on it: its score for Germany says nothing about its French rules.
- **One verdict per document.** A library can be right for the wrong reason: rejecting a document under an unrelated rule gets 0.5, and the S of the same library shows whether it rejects too much.

## Outputs

Each harness writes one JSON line per library and per suite, to `cases_<lang>.jsonl` (`cases_<module>.jsonl` for the Go bench):

```json
{"lang":"java","lib":"phive","pkg":"com.helger.phive:phive-xml+phive-rules-{en16931,xrechnung,zugferd}","version":"12.3.0/4.7.1",
 "suite":"en16931",
 "results":[{"case":"en16931/cii-000-br-02-invoice-number.xml","errors":1,"rules":["BR-02"]},
            {"case":"…","errors":0,"rules":[]},
            {"case":"…","errors":0,"rules":[],"error":"exception message"}],
 "note":"how the library is called"}
```

`errors` is the number of errors, `rules` the sorted, distinct identifiers (or messages) reported, `error` an exception or a crash.

## Running

```bash
./gen.sh                            # regenerate the mutation cases (Go; ZERECHNUNG_DIR to use a local clone)
./fetch.sh                          # fetch the KoSIT test suite
./confirm.sh                        # run the reference, record the verdicts in cases.tsv
cd .. && ./run.sh cases             # all nine languages (or: ./run.sh cases java rust)
cd ../go && ./run.sh cases          # the Go libraries (or: ./run.sh cases facturx kanjo)
```

`gen.sh` and `confirm.sh` are only needed to change the cases; `cases.tsv` is versioned. The confidence tables are part of the `tables.md` written by each report tool; they need the `cases_*.jsonl` files of the same results folder.

## Adding a country

1. Add a line to `suites.tsv`: name, syntaxes, countries (ISO codes), title, reference (`<lang> <lib>` of one of the harnesses), a glob of external files if any, and the rules of the norm the reference does not check.
2. Put the documents in a folder named after the suite, or list external files in `fetch.sh`, then run `cd tool && go run . index`.
3. Run `confirm.sh` (or the reference's harness and `tool confirm`); describe the reference in `References` and the country in `CountryNames` (`markdown.go`).
