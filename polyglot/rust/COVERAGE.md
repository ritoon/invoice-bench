# Coverage: Rust ecosystem

Rust bench for the common protocol (`../PROTOCOL.md`). One binary crate per
library (`libs/<lib>`, package `bench-<lib>`), a shared harness (`harness`),
versions pinned with `=x.y.z` and a `Cargo.lock`. Toolchain: rustc / cargo
1.93.1, `release` profile by default.

The evidence cited is paths in the sources of the crates downloaded by Cargo
(`~/.cargo/registry/src/index.crates.io-*/<crate>-<version>/…`).
License, latest version and downloads come from the crates.io API
(`/api/v1/crates/<name>`, as of 2026-11-17; downloads: total, and over 90 days
in parentheses when they differ).

## Measured libraries

### en16931 + en16931-formats 0.10.1 (hupe1980)

EN 16931 semantic model and rules reimplemented in Rust, CII and UBL readers
and writers, ZUGFeRD / Factur-X extraction and embedding (features `cii`,
`zugferd`). No XSD or XSLT is executed: the rules are code.

- Artifacts: CEN `validation-1.3.17` (`en16931-0.10.1/src/lib.rs:95`, code
  lists generated in `src/codes/generated.rs:6`); KoSIT
  `xrechnung-schematron` v2.6.0, i.e. XRechnung 3.0.x
  (`src/profiles.rs:26-31`); Peppol BIS Billing 3.0.21 (`src/profiles.rs:46`).
- Rules: in `src/validation/`, 60 BR identifiers, 28 BR-CO, 23 BR-CL and
  21 BR-DEC, plus the VAT category families generated by the `family!` macro
  (`src/validation/rules/category.rs:395`). There are also 25 BR-DE,
  14 BR-DEX and 5 BR-DE-CVD (`rules/xrechnung.rs`), as well as 64 PEPPOL
  identifiers (`rules/peppol.rs`).
- Syntax layer: 447 of CEN's 522 CII-SR / CII-DT `not(…)` assertions; the
  other 75 need an XPath engine and are not carried over
  (`en16931-formats-0.10.1/src/cii/prohibitions_generated.rs:10-13`).
  CII-SR-465 is not among them.
- Factur-X: the four profiles are used to classify the document. MINIMUM and
  BASIC WL run only the totals rules; BASIC and EXTENDED run the core rules.
  FeRD-specific rules are not shipped (`src/profiles.rs:6-9`).
- Container: `receive` on a PDF compares the XMP (`fx:ConformanceLevel`, file
  name, `/AFRelationship`, `pdfaid:part`) with the attachment and BT-24
  (`en16931-formats-0.10.1/src/zugferd/extract.rs:22-83`). There is no
  ISO 19005 check.
- Embedding: by incremental update (`src/zugferd/embed.rs:1-17`). It refuses
  a host that already carries Factur-X metadata. Both protocol hosts have an
  XMP containing the `fx:` namespace, hence the `fail` on `Embed_Small` and
  `EmbedClassic_Small`.
- Measured validation: `receive(Policy::default())`, which applies the
  profile declared by BT-24 (BR-DE on the XRECHNUNG files). Fatal entries
  from the layers and `fatal()` findings are counted.
- Network: none.

### einvoice-validator 0.4.0 (+ einvoice-xsd, einvoice-pdf)

Runs the official artifacts without Java: an XSD, XPath and XSLT 2.0 engine
written in Rust (`einvoice-xsd`, `einvoice-xpath`, `einvoice-xslt`…).

- Bundled by default: the official CEN EN 16931 CII 1.3.17 XSLT, unmodified
  (`bundles/cen-cii/bundle.toml:9`, `bundles/cen-cii/cii/xslt/EN16931-CII-validation.xslt`,
  810 rule identifiers), and the UN/CEFACT CII D16B XSDs (`einvoice-xsd`).
  The README claims that its verdicts match Saxon-HE on the CEN 1.3.17 test
  corpora.
- Offline, this is the only rule set. Factur-X 1.09.2
  (`pins/fetch-facturx.pins:1`), XRechnung 3.0.2 / schematron 2.6.0
  (`pins/fetch-xrechnung.pins`), the French rules and Peppol 3.0.22
  (`pins/fetch-peppol.pins:1`) are downloaded with the `fetch` feature
  (`Cargo.toml:42-60`, `src/rulesets/mod.rs:15`). That feature is not
  enabled here: the HTTPS client is not compiled.
- In the CEN XSLT, CII-SR-465 has the `warning` flag. A pure CEN validation
  therefore flags 2 files out of 26, not 6.
- No invoice model, so Parse and Write are `unsupported`.
  `pdf::extract` returns the XML, the `/AFRelationship` and the XMP without
  checking them: CheckPDF is `unsupported`.
- `rust-version = "1.99"` is declared in every published version, but the
  crate compiles with 1.93.1. Hence `--ignore-rust-version` in `run.sh`.

### erechnung-validator 0.1.1 (Promaris)

Replays KoSIT and Mustang side by side with their artifacts, on an
XSLT / Schematron engine written in Rust (`oxixml-*` 0.1.2). No Java.

- KoSIT: XRechnung 3.0.2 configuration, scenarios
  `artefakte/kosit/scenarios-xrechnung-3.0.2.xml` (CHANGELOG as of 2026-01-31),
  CII D16B XSD, CEN `EN16931-CII-validation-1.3.16.sch` (`src/kosit/szenario.rs:32`),
  `XRechnung-CII-validation.xsl` (28 BR-DE, 7 BR-DEX, 6 BR-DE-CVD). Sources
  in `NOTICE.md`.
- Mustang 2.26.0: Factur-X 1.09.2 XSD and Schematron for the five profiles
  (`artefakte/mustang/sch/FACTUR-X_EN16931.sch:2-5`, "Version: 1.09.2"),
  XRechnung 3.0 on the Mustang side (`artefakte/mustang/xr/XR_30`). These are
  the most complete Factur-X profile rules in the ecosystem (196
  identifiers in `FACTUR-X_EXTENDED.xslt`).
- No BR-FR: the EXTENDED-CTC-FR variant is not bundled. No
  Peppol.
- Measured validation: `beide(Szenarien::Automatisch)`. The errors of both
  tools are added up, prefixed `KoSIT:` or `Mustang:`. It is the only
  library that matches the reference of 6 files out of 26.
- CheckPDF: `beide_pdf` is the library's native function, but it only
  extracts the XML and then validates it. `src/pdf.md` says so: "Keine
  PDF/A- oder veraPDF-Prüfung". The benchmark note states this.
- Extract: the `pdf` module is private (`src/lib.rs:24`), hence `unsupported`.
- Network: none.

### core-invoice + core-invoice-formats 2.0.3 (proxeon)

EN 16931 and PINT model with its rules in Rust, UBL 2.1 and CII D16B codecs.

- Rules aligned with CEN `validation-1.3.16` (`core-invoice-2.0.3/src/codes.rs:17`).
  There are 58 BR, 23 BR-CO, 23 BR-CL, 21 BR-DEC and 98 VAT category
  rules. Peppol BIS v3.0.20 (`codes.rs:19`, 60 PEPPOL identifiers),
  PINT 1.1.2 and PINT-MY 1.3.0.
- BR-DE: 25 rules behind the optional `xrechnung` feature, enabled here
  (`src/xrechnung.rs:1-6`). The README states "Not KoSIT Valid"
  (`README.md:57`).
- `validate_xml` applies neither XSD nor CII-SR
  (`core-invoice-formats-2.0.3/src/lib.rs:179-189`). The generated CII-SR
  prohibitions (`src/prohibitions_cii.rs`) are only used when writing
  (`lib.rs:298`).
- The reader rejects TypeCodes 204 and 387 ("malformed"): 3 files out of
  26 cannot be parsed.
- Validation: 4 of the 7 flags come from the rules, which produce false
  positives (BR-32, BR-37, BR-CO-11/12/13, BR-S-08 on valid examples). The
  other 3 are parse errors.
- No PDF. Network: none.

### zugferd-rs 0.2.2 (philipp-berger)

Model, CII and UBL readers and writers (including an XRechnung CII variant),
PDF via lopdf 0.47, XSD and Schematron validation via libxml2.

- XSD: Factur-X 1.09.2 / ZUGFeRD 2.5.2 and 1.08, per profile
  (`assets/schemas/cii/`, `src/validator/xsd.rs:19-27`).
- Schematron: the preprocessed `.sch` of CEN `validation-1.3.17`
  (`assets/schemas/schematron/PROVENANCE.md`) is evaluated in XPath 1.0 by
  libxml2. Rules that need XPath 2.0 are skipped and marked `SKIP:`, and the
  result is declared incomplete (`src/validator/schematron.rs:1-20`).
  Every failed assertion becomes an `Error`, whatever its flag
  (`schematron.rs:315-318`). The CEN warnings CII-SR-119 and CII-SR-465
  therefore count as errors, while BR-CL-25 is not found.
- Saxon-HE (Java) is available as an option, called only if the caller asks
  for it (`src/validator/external.rs:1-5`). Not used here: Java is absent.
- Container: `validate_pdf_a` applies 21 rules taken from the veraPDF
  PDF/A-3b profiles (`src/pdfa/rules_generated.rs:1-9`), but without checking
  the XML. CheckPDF is therefore `unsupported`.
- Embedding: `embed_xml` rewrites the PDF as PDF/A-3b (Factur-X XMP, sRGB
  OutputIntent). It converts the host, which the note points out.
- The reader rejects TypeCodes 204, 387, 575 and 877: 19 files out of 26
  parsed, and `Parse_Large` is a `fail`.
- System dependencies: libxml2 (pkg-config) and libclang (bindgen in the
  `build.rs` of `libxml` 0.3.24). The XSDs and the `.sch` are read at run
  time from `assets/schemas`: `run.sh` exports `ZUGFERD_SCHEMAS_DIR`, found
  through `cargo metadata`.
- Network: none.

### factur-x 0.3.1 and pdfa 0.1.10 (cipansor/crateworks)

Two sister crates, one for the XML, the other for the container.

- factur-x: EN 16931 model, CII and UBL parsing and writing.
  - `validate` checks 16 arithmetic rules (`src/validate.rs`: BR-01 to
    BR-06, BR-09, BR-16, BR-CO-10, BR-CO-13 to BR-CO-18, BR-S-08). The README
    advertises "BR-CO-10 to BR-CO-18" (`README.md:78-79`), but BR-CO-11 and
    BR-CO-12 are missing.
  - The profile is only detected (`profile_of`).
  - Amounts with four decimals are rejected ("9.9000"): 9 files out of 26
    parsed.
- pdfa:
  - `check_factur_x` checks five container points: PDF/A-3 XMP,
    `/Metadata`, attachment name, `/AFRelationship` and checksum (README,
    `src/conformance.rs:106`). It does not check the XML, so CheckPDF is
    `unsupported`.
  - `embed` refuses object streams and xref streams
    (`src/container.rs:273-274`): `fail` on `host.pdf`, `ok` on
    `host_classic.pdf`.
  - `embedded_file` finds the first `/Type /EmbeddedFile` stream by byte
    search: 32 PDFs out of 104.
- Single dependency: `xmlkit`, from the same repository. Network: none.

### pdf-invoice 1.5.0 (PDFluent SDK)

FDF/XFDF and a ZUGFeRD / Factur-X CII model, on a fork of lopdf
(`pdfluent-lopdf =0.39.9`, `Cargo.toml:61-63`). License: AGPL-3.0 or
commercial.

- The model stores amounts as `f64`.
- `validate_en16931` covers 14 rules (`src/validation.rs`: BR-01 to BR-08,
  BR-CL-01, BR-CL-04, BR-CO-10, BR-CO-13, BR-CO-15, BR-S-08).
- `validate` checks the fields required by the profile. In particular it
  requires `buyer_reference` and `payment_means` in EN16931, which produces
  false positives on 20 of the 26 valid examples.
- `to_xml` refuses to write a model that does not pass these checks: `fail`
  on `Write_*`.
- Extraction: one name at a time, in the root `/Names` array. 101 PDFs out of
  104; "/EF not a dict" on three Gnuaccounting PDFs.
- Embedding: rewrites the whole file and replaces the XMP, without PDF/A
  conversion.
- No XSD, no UBL, no container check. Network: none.

### zugferd 0.3.0 (FaultierSP)

Generator only: an `InvoiceBuilder` produces MINIMUM, BASIC WL or BASIC XML
(serde + quick-xml).

- No reader, no PDF.
- `validate_business_rules` (`src/components/business_rules.rs:104`) only
  applies to the built model: 17 identifiers, including a made-up one,
  "BR-7890".
- `Write_Small` uses a hand-built model based on `EN16931_Einfach`, at
  BASIC level. The builder requires an order reference (BT-13) and a due date,
  both missing from the example: they are set to "-" and to the payment terms
  date. `Write_Lines` is skipped.

### einvoice 0.1.1

CII and UBL models generated for a fork of yaserde
(`einvoice_deps_yaserde =0.0.1`).

- The rule validators are stubs: 777 functions of the form
  `if false { return Err(…) }` on the CII side and 967 on the UBL side
  (`src/cii/cii_business_rule_validator.rs`). Validate is therefore
  `unsupported`.
- `validate_zugferd_pdf` takes a file path, and extraction is
  private (`src/lib.rs:146,165`).
- Measured: Parse (`yaserde::de::from_str`) and Write
  (`yaserde::ser::to_string`).

### lopdf 0.47.0 (floor)

A general-purpose PDF library, not a Factur-X library. It serves as the
extraction floor: full load, walk of `/Names/EmbeddedFiles` with `/Kids`, then
inflate, all written by hand in `libs/lopdf/src/main.rs`. zugferd-rs,
en16931-formats, erechnung-validator and einvoice rely on lopdf, in versions
from 0.34 to 0.47.

## Build and measurement notes

- Each package is built separately (`cargo build -p bench-<lib>`), so that
  each binary only has the features of its own dependencies.
  `--locked --ignore-rust-version`: see einvoice-validator.
- `RAYON_NUM_THREADS=1`: lopdf, with its default features (zugferd-rs,
  pdf-invoice, einvoice), parses objects with rayon. The protocol requires
  a single thread.
- CPU time and peak memory: `getrusage(RUSAGE_SELF)` (crate `libc` 0.2.191,
  pinned), user + system time of all threads, read before and after each
  series (`cpu_ns_per_op`); `ru_maxrss` (bytes on macOS) read at the end of
  the series in the `resources` pass, where `run.sh` runs
  `target/release/bench-<lib> resources <Bench>` directly, one process per
  benchmark. Even with `RAYON_NUM_THREADS=1`, rayon keeps a worker thread
  next to the measured thread: lopdf parsing runs there while the measured
  thread waits, hence a CPU time of about 105% of wall-clock time in
  extraction and embedding for zugferd-rs. No library starts a child process
  (the Saxon option of zugferd-rs is not used).
- The body of each binary runs in a thread with a 512 MiB stack. The
  official stylesheets recurse deeply: erechnung-validator asks for 64 MiB.
- `first_call_ns` includes the lazy compilation of the stylesheets:
  `Validator::cen_cii()` in a `OnceLock` (einvoice-validator) and the
  erechnung-validator cache.
- Security review before building: `build.rs` files and proc-macros of the
  rarely downloaded crates (`einvoice_deps_yaserde_derive`, `multiversion_no_op`,
  `libxml`, `oxixml-*`, `einvoice-*`). No network access, no file outside the
  build directory. Only `libxml` queries pkg-config and runs bindgen on the
  system headers.
- In the compiled sources, the only occurrences of `std::net` parse IPv6
  addresses in IRIs (`oxixml-iri`, `einvoice-xsd`). The HTTPS client of
  einvoice-validator is not compiled (`fetch` feature inactive); the Saxon
  module of zugferd-rs (`validator::external`) is compiled but never called.
